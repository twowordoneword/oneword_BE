# 뮤징(musing) — 설계 의사결정 기록 (ADR)

> 백엔드 스키마·API를 설계하며 내린 주요 결정과 근거를 기록한 문서.
> 각 항목은 **배경 → 선택지 → 결정 → 근거 → 트레이드오프** 순서로 정리한다.

---

## ADR-001. 곡을 별도 테이블로 분리 (정규화 vs 임베드)

**배경**
일기에는 "나의 음악"과 "오늘의 추천곡"이 붙는다. 곡 정보(제목·가수·앨범·커버 URL·미리듣기 URL)를 어디에 저장할지 결정해야 했다.

**선택지**
- (A) DIARIES 테이블에 곡 필드를 직접 임베드 (`my_track_name`, `today_track_artist` …)
- (B) TRACKS 마스터 테이블로 분리하고 참조 (정규화)

**결정** → (B) 정규화

**근거**
- 같은 곡이 여러 날 등장할 수 있어 임베드 시 데이터가 중복된다.
- 커버 URL 등 곡 메타가 바뀌면 여러 행을 고쳐야 하는 **갱신 이상(update anomaly)** 발생.
- "가장 많이 고른 곡" 같은 **통계 화면** 요구가 있어, 곡을 식별 가능한 엔티티로 두는 편이 집계에 유리하다.

**트레이드오프**
- 조인이 늘고, 일기 저장 시 "있으면 재사용, 없으면 삽입"하는 **upsert 로직**이 필요해 구현이 복잡해진다.
- 만약 앱이 단순 기록용이고 통계가 없었다면 임베드안이 더 합리적이었을 것.

## ADR-002. MY / RECOMMENDED를 role 컬럼으로 구분

**배경**
한 일기에는 사용자가 고른 곡(MY)과 서버가 추천한 곡(RECOMMENDED) 두 종류가 붙는다.

**선택지**
- (A) DIARIES에 `my_track_id`, `today_track_id` 두 개의 FK 컬럼
- (B) 중간 테이블 DIARY_TRACKS에 `role`(MY|RECOMMENDED) 컬럼으로 구분

**결정** → (B) 중간 테이블 + role

**근거**
- 나중에 "친구 추천곡", "두 번째 추천" 등 역할이 늘어도 **컬럼 추가 없이 role 값만 확장**하면 된다.
- `UNIQUE(diary_id, role)` 제약으로 "일기당 MY 1개, RECOMMENDED 1개" 규칙을 **DB가 강제**한다.

**트레이드오프**
- 두 FK 컬럼 방식보다 조회 시 조인이 한 번 더 필요하고 살짝 복잡하다.
- 현재 역할이 2개뿐이라 오버엔지니어링으로 보일 수 있으나, 확장성과 정합성을 우선했다.

## ADR-003. "하루 한 개 일기"를 DB 유니크 제약으로 보장

**배경**
뮤징의 핵심 컨셉은 "하루 한 줄". 같은 사용자가 같은 날짜에 일기를 두 개 만들 수 없어야 한다.

**선택지**
- (A) 애플리케이션 코드에서 저장 전 조회 후 존재하면 거부
- (B) `UNIQUE(user_id, diary_date)` DB 제약

**결정** → (B) DB 제약 (앱 검증은 UX용으로 병행)

**근거**
- 앱의 "날짜 선택 → 일기 조회" 흐름 덕분에 프론트는 이미 작성 여부를 알고 POST/PUT을 가른다. 하지만 이는 **UX 판단일 뿐, 데이터 무결성을 보장하지 않는다.**
- 서버는 클라이언트를 신뢰할 수 없다. 프론트의 조회 결과는 **그 순간의 스냅샷**이라 저장 시점엔 낡아 있을 수 있고, 다음과 같은 경우 프론트 검사로는 막지 못한다:
  - 저장 버튼 연타·중복 전송 (두 요청이 모두 "없음"을 보고 둘 다 INSERT)
  - 두 기기 동시 사용, 네트워크 타임아웃 후 자동 재시도
  - 프론트를 거치지 않은 API 직접 호출
- (A)만 쓰면 **조회와 저장 사이의 경쟁 조건(race condition)**으로 중복이 들어갈 수 있다.
- DB 유니크 제약은 이를 원천 차단하여, 비즈니스 규칙을 **데이터 무결성 레벨**에서 지킨다. → 프론트 조회(UX) + DB 제약(안전장치)의 **방어적 설계(defense in depth)**.

**트레이드오프**
- 중복 저장 시 DB가 예외를 던지므로, 서버가 이를 `409 DIARY_ALREADY_EXISTS`로 변환해 처리해야 한다.

## ADR-004. mood / weather를 한글 문자열로 저장

**배경**
기분 8종(기쁨·우울·…)·날씨 5종(맑음·흐림·…)은 화면 표시뿐 아니라 **추천 태그 매핑의 키**로도 쓰인다(예: 기쁨→k-pop).

**선택지**
- (A) 한글 문자열 그대로 저장
- (B) 영문 코드 enum(JOY 등) 저장 + 화면에서 변환
- (C) 별도 mood/weather 테이블로 정규화

**결정** → (A) 한글 문자열 + `CHECK` 제약

**근거 (특히 C를 왜 안 골랐나)**
- 별도 테이블(C)이 값어치를 하는 조건은 ① 값이 동적으로 늘어나거나, ② 값마다 부가 속성(아이콘·색·정렬순서·다국어 라벨·태그 매핑)이 붙거나, ③ 관리자가 데이터로 수정할 때다.
- 하지만 mood 8종/weather 5종은 **프론트 UI에 버튼으로 박혀 있고 추천 로직 코드에 매핑이 하드코딩된 "닫힌 집합"**이다. 기분 하나를 추가하려면 어차피 프론트(버튼·아이콘)와 추천 코드를 새로 배포해야 하므로, 테이블이 주는 "코드 수정 없이 값 추가" 유연성이 **실제로는 발생하지 않는다.**
- 그 결과 C는 **모든 일기 조회마다 JOIN + 시드 데이터 관리 비용**만 늘린다. 정작 핵심 이득인 무결성(허용값만 저장)은 `CHECK` 제약이 JOIN 없이 동일하게 보장한다.
- (B) 영문 코드 대신 (A) 한글 문자열을 택한 이유: 이 값이 추천 태그 매핑의 키로 그대로 쓰여, **프론트·API·DB가 같은 문자열을 공유**하면 변환 계층이 사라져 매핑 버그가 준다.
- 요약: C가 틀린 게 아니라, **이 요구사항(닫힌 집합·클라이언트 결합)에서는 얻는 이득이 없어** 과설계다.

**트레이드오프**
- **다국어 지원**이 어려워지고(한글이 DB에 박힘), 값 변경 시 마이그레이션 부담이 있다.
- 확장성을 일부 포기하고 **일관성과 개발 속도**를 택한 결정 — 정답이 갈리는 지점임을 인지하고 선택했다.

**재검토 트리거 (이때는 C로 전환)**
- 기분/날씨에 아이콘·색·정렬순서 등 **부가 속성**이 필요해지거나,
- **다국어**를 지원하거나,
- 값 집합을 **관리자/운영이 코드 배포 없이** 바꿔야 할 때.
- → 이 경우 mood/weather 룩업 테이블을 도입하는 새 ADR을 작성하고 본 ADR을 *Superseded* 처리한다.

## ADR-005. 추천 로직을 클라이언트 → 서버로 이전 (보안)

**배경**
초기 프론트는 Last.fm API를 **직접 호출**했고, API 키가 앱 코드에 하드코딩되어 있었다.

**선택지**
- (A) 현행 유지 (클라이언트에서 외부 API 직접 호출)
- (B) 추천을 서버 엔드포인트로 옮기고 키를 서버 환경변수로 은닉

**결정** → (B) 서버 이전

**근거**
- 클라이언트에 키가 박히면 **앱 디컴파일로 키 탈취**가 가능해 보안 취약점이다.
- 서버로 옮기면 키 은닉 + 외부 API 응답 캐싱·요청 제어까지 가능해진다.

**트레이드오프**
- 서버가 외부 API 장애·지연을 떠안게 되어, 타임아웃·폴백(`502 EXTERNAL_API_ERROR`) 처리가 필요하다.

## ADR-006. 일관된 API 응답 래퍼와 버전 프리픽스

**배경**
프론트가 성공/실패를 일관되게 처리하고, 향후 스펙 변경에 대비할 필요가 있었다.

**선택지**
- (A) 엔드포인트마다 자유로운 응답 형태
- (B) 공통 래퍼 `{ success, data }` / `{ success, error }` + `/api/v1` 프리픽스

**결정** → (B)

**근거**
- 프론트가 **단일 규칙**으로 응답을 파싱하고 에러를 처리할 수 있다(에러코드 표준화).
- 버전 프리픽스로 이후 **v2와 병행 운영**이 가능해 하위 호환을 지킬 수 있다.

**트레이드오프**
- 모든 응답에 래핑 오버헤드가 붙고, 서버에 공통 응답/예외 처리 레이어를 구현해야 한다.

## ADR-007. 참조 무결성과 삭제 정책 (ON DELETE CASCADE)

**배경**
사용자·일기를 삭제할 때 연결된 하위 데이터의 처리 방식을 정해야 했다.

**결정**
- `diaries.user_id`, `diary_tracks.diary_id` 등에 **FK + ON DELETE CASCADE** 적용.
- 단, **TRACKS 마스터는 삭제하지 않는다**(다른 일기가 참조할 수 있으므로).

**근거**
- 일기를 지우면 그 일기의 곡 연결(DIARY_TRACKS)만 자동 정리되어 **고아 레코드(orphan)**가 남지 않는다.
- 곡 마스터를 보존해 재사용성과 통계 일관성을 유지한다.

**트레이드오프**
- Cascade는 편리하지만 대량 삭제 시 연쇄 삭제 비용이 있고, 실수로 상위 삭제 시 하위가 함께 사라진다. (필요 시 soft delete로 전환 가능하도록 여지를 둠.)

## ADR-008. JWT 인증 + 리프레시 토큰 DB 저장

**배경**
OAuth 로그인(카카오·네이버·구글·애플) 후 자체 세션을 어떻게 유지할지 결정해야 했다.

**선택지**
- (A) 액세스 토큰만 사용 (짧으면 잦은 재로그인, 길면 탈취 위험)
- (B) 액세스(단기) + 리프레시(장기) 토큰, 리프레시는 **무상태**(DB 미저장)
- (C) 액세스 + 리프레시 토큰, 리프레시를 **DB 저장**

**결정** → (C) 액세스 + 리프레시, 리프레시 토큰은 해시로 DB 저장

**근거**
- 액세스 토큰을 단기(예: 1h)로 두어 탈취 피해 창을 줄이고, 리프레시 토큰(예: 2주)으로 재로그인 없이 갱신 → 보안과 UX를 동시에 잡는다.
- 리프레시 토큰을 DB에 두면 **로그아웃·기기별 세션 관리·강제 무효화**가 가능하다. 무상태(B)는 만료 전 강제 종료가 불가능하다.
- 토큰 원문이 아닌 **해시**를 저장해, DB 유출 시에도 토큰이 바로 악용되지 않게 한다.

**트레이드오프**
- 테이블(refresh_tokens)과 갱신 시 조회 비용이 추가된다. 만료 토큰 정리 배치도 필요.
- 규모가 커지면 Redis 등으로 옮기는 편이 빠르지만, 초기엔 RDB로 충분하다.

## ADR-009. OAuth 4종 채택 · 로컬(이메일/비번) 로그인 배제

**결정** → `kakao` `naver` `google` `apple` 지원, 자체 비밀번호 로그인은 두지 않음.

**근거**
- 개인 음악 일기 앱 특성상 가입 마찰을 줄이는 소셜 로그인이 적합하고, 비밀번호 저장·재설정·보안 부담을 회피한다.
- `users.provider` + `provider_id`로 출처를 일반화해, provider 추가 시 스키마 변경이 없다.

**트레이드오프**
- Apple 로그인은 iOS 앱 심사에서 사실상 필수라 초기부터 포함. 대신 각 제공자별 콜백·토큰 검증 구현 부담이 있다.

## ADR-010. 음악 데이터 소스 이전 (Last.fm/Spotify → Apple + ReccoBeats)

**배경**
초기 추천 로직은 Last.fm(태그·유사 아티스트)에 의존했고 API 키가 클라이언트에 노출돼 있었다.

**문제**
- Last.fm은 **상업 이용 시 별도 계약**(partners@last.fm)이 필요 — 사실상 무료 상업 사용 불가.
- Spotify는 2024-11-27부터 **신규 앱의 추천·오디오특성·유사아티스트·30초 미리듣기 API 차단**.

**결정** → 검색·메타·커버·미리듣기는 **iTunes Search + Apple Music RSS**(무료·상업 가능), 곡 감정 특성은 **ReccoBeats**(무료). 폴백/보강은 **Essentia 자체분석**(미리듣기 직접 분석). **AcousticBrainz 덤프는 채택하지 않음**(수십 GB 저장·운영 부담, 2022 컷오프).

**근거**
- Apple 계열은 스토어 홍보 목적 내에서 상업 이용이 허용되고 무인증으로 쓸 수 있다.
- ReccoBeats가 Spotify 오디오 특성(valence·energy 등)을 무료로 대체한다.

**ReccoBeats 약관 확인 (2026-05-25 기준)**
- **상업 이용 명시 허용** — "personal and commercial projects 모두 무료", API 키 불필요. (Last.fm과 달리 별도 계약 없음)
- **주의①** 곡 기초 메타(곡명·아티스트·앨범)는 **Spotify 유래**이며 그 사용의 제3자 약관 준수는 사용자 책임. → 우리는 메타·커버는 iTunes에서 받고 ReccoBeats는 **감정 특성값(고유 분석 데이터)만** 사용하므로 이 리스크를 회피.
- **주의②** 개인 운영·무보증(AS-IS), 예고 없이 종료 가능 → **의존성 리스크**.

**트레이드오프**
- Apple 차트는 인기곡 위주라 롱테일·신선함이 약하고, '유사 아티스트'는 "동일 아티스트+장르"로 근사한다.
- iTunes 20콜/분 + ReccoBeats(비공개 한도, 429) → `tracks` 특성 캐시 + 차트 일 캐시로 흡수.
- ReccoBeats 종료 대비: 캐시로 기존 값 보존 + **FeatureProvider 인터페이스**로 Essentia 자체분석 구현체로 교체 가능(곡 매칭 문제도 우회).
- ReccoBeats의 조회 방식(곡 ID vs 파일 업로드)은 구현 시 검증 필요.

## ADR-011. 감정 좌표 기반 추천 · LLM 미채택 · 프라이버시 우선

**배경**
추천이 앱의 핵심 가치. "장르 인기차트 무작위"로는 감정 적합도가 낮다. 반면 일기 텍스트를 LLM으로 해석하면 품질은 오르나 사생활 문제가 있다.

**선택지**
- (A) 기분→장르→인기차트 무작위
- (B) **감정 좌표(valence-arousal) 매칭** — 기분/날씨/계절을 좌표로, 후보곡을 특성값으로 랭킹
- (C) LLM이 일기 본문(또는 제목)을 읽어 추천/보정

**결정** → (B) 감정 좌표 매칭 채택. (C) LLM은 **미채택**. 입력은 `mood·weather·date·seed`뿐이며 일기 텍스트는 외부로 보내지 않는다.

**근거**
- (B)는 감정을 정량적으로 매칭해 적합도가 높고, 알고리즘을 직접 설계·구현하므로 기술적 깊이(추천 시스템)를 보여준다.
- (C)는 ① 일기가 제3자(LLM 제공자)로 전송되어 **사생활·PIPA 국외이전** 문제, ② 존재하지 않는 곡 **할루시네이션**, ③ 비용·지연이 발생. 제목만 보내도 "이별했다" 등 민감정보일 수 있어 위험이 사라지지 않는다.
- 포트폴리오 관점에서도 **AI를 절제한 판단**과 그 근거 기록이 억지 AI 기능보다 강한 시그널이다.

**트레이드오프**
- 8개 기분 라벨 + 날씨/계절만으로는 일기 본문의 미묘한 결을 놓친다.
- **확장 경로**: 텍스트 이해가 필요하면 **온디바이스**로 감정 추출(원문 미전송, 좌표값만 서버로) → "privacy-by-design" 셀링포인트. 클라우드 LLM은 명시적 동의 + 무보존 시에만.

## ADR-012. 앱스토어(iOS) 실배포 대응

**배경**
포트폴리오를 넘어 App Store 실제 배포가 목표. 애플 심사 규정과 외부 의존성 안정성을 설계에 반영해야 한다.

**결정 / 대응**
- **계정 삭제(Guideline 5.1.1)**: `DELETE /auth/withdraw` 제공. FK `ON DELETE CASCADE`로 유저 삭제 시 일기·곡연결·리프레시토큰 일괄 삭제. (ADR-007 설계가 그대로 요구사항 충족)
- **Sign in with Apple(Guideline 4.8)**: 카카오·네이버·구글 제공 → Apple 로그인 필수 포함. provider 4종에 이미 반영(ADR-009). UI 동등 노출.
- **개인정보 처리방침 + App Privacy 라벨**: 일기 텍스트 외부 미전송(ADR-011)이라 수집 최소화로 유리.
- **의존성 degradation**: ReccoBeats(개인 운영·종료 가능) 장애 시 감정 랭킹을 건너뛰고 기분→장르→차트로 폴백. FeatureProvider 인터페이스로 Essentia 자체분석 구현체로 교체 가능.

**근거**
- 계정 삭제·SIWA는 미충족 시 **리젝 사유**라 설계 단계에서 확정해야 재작업이 없다.
- 실서비스는 단일 외부 서비스 장애로 핵심 기능이 죽으면 안 된다 → 폴백 필수.

**트레이드오프**
- 계정 삭제는 되돌릴 수 없으므로(hard delete) 삭제 전 확인 단계를 UI에 둔다.
- 폴백 경로는 추천 품질이 낮아지지만, 가용성을 우선한다.
