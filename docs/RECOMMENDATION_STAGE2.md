# 추천 2단계 — 곡 감정값 채우기

> 1단계(감정 좌표 매핑 + iTunes 후보 랜덤)는 완료.
> 2단계는 **곡마다 valence·energy를 채워서 거리 랭킹을 켜는** 것.
> 설계 배경은 `RECOMMENDATION.md`, 이 문서는 "어떻게 만들지".

---

## 1. 결정 요약

| 항목 | 결정 |
|---|---|
| 감정값 소스 | **FreqBlog API** (이름+아티스트 조회) |
| 실행 방식 | **배치**로 미리 채움 (요청 시 외부 호출 없음) |
| 후보 풀 | **`tracks` 테이블** (차트 + 설문 + 사용자 곡) |
| 미채택 | ReccoBeats(매칭 불가), Essentia 직접 실행(라이선스) |

### 왜 FreqBlog인가
- **곡 매칭 문제가 없다.** 이름+아티스트로 조회 — ISRC·Spotify ID 불필요.
  (ReccoBeats는 제목만 매칭 → `Shape of You` 검색 시 상위가 전부 커버곡이라 실패)
- **국내 곡이 해결된다.** 한국 카탈로그 10,500곡 + **미보유 곡은 즉석 백필**
  (iTunes 미리듣기를 받아 Essentia로 분석 후 등재, 약 15초). 무료 티어에도 포함.
- **상업 이용 가능.** 유료 API지만 라이선스가 명확하다.
- `POST /bulk`로 **한 번에 50곡** 조회 → 5,000곡이 100회 호출.

### 왜 Essentia를 직접 안 돌리는가
- 라이브러리는 오픈소스지만, **감정 예측 사전학습 모델(MTG)이 CC BY-NC-SA = 비상업 전용**이다.
  상업 서비스로 쓰려면 별도 라이선스 협상이 필요 → 설계 원칙 §1 "상업 이용 가능한 소스만"에 위배.
- FreqBlog도 내부적으로 Essentia를 쓰므로 **분석 품질은 동일**하고, 라이선스만 해결된다.

### 비용 (실측 요금표)
| 플랜 | 월 요금 | 월 요청 |
|---|---|---|
| Free | £0 | 1,000 |
| Hobbyist | £9.99 | 15,000 |
| Starter | £39 | 150,000 |
| Pro | £129 | 750,000 |

- **초기 5,000곡**: Hobbyist 한 달(≈2만원) 후 해지 **또는** Free로 5개월 분할(0원).
- **운영 단계**: 신규 곡 월 150~200건 → **Free 티어로 충분**.
- ⚠ `£0.17/1k`는 Pro 플랜 단가다. 낱개 종량 구매는 없다.

### 한계 — valence는 덜 정확하다
음악 감정 인식은 **arousal은 잘 맞고 valence는 약하다**(연구 다수: R² arousal 0.56~0.75 vs valence 0.29~0.53).
소리만으로는 밝고 어두움을 잡기 어렵기 때문(가사·화성·맥락 의존). FreqBlog·Essentia 공통 한계.
- 우리는 **절대값이 아니라 순서**만 필요하므로 극단 구간은 쓸 만하다.
- **검증 방법**: 설문(§3.6)에서 "슬플 때 듣는 곡"과 "신날 때 듣는 곡"의 valence 평균이
  실제로 갈리는지 확인한다. 안 갈리면 valence 가중치를 낮추거나 장르를 보조 신호로 쓴다.

## 2. 후보 풀 = `tracks`

추천이 iTunes를 실시간 호출하지 않고 **DB에서 뽑는다.**

```
[기존 1단계] 추천 요청 → iTunes 검색 → 후보 25곡 → 랜덤
[2단계]      추천 요청 → tracks에서 목표 좌표에 가까운 곡 조회 → 상위 30곡 중 고정 시드 선택
```

- `tracks`에 곡이 들어오는 경로는 **세 가지**(차트·설문·사용자)이며 **모두 후보로 쓴다.** → §3.0
- 어느 경로로 들어왔든 처리 규칙은 같다: **감정값이 비었고 미리듣기가 있으면 채운다**(§4).
- `origin` 컬럼으로 출처만 구분해둔다 — 나중에 "차트 곡만" 처럼 좁히고 싶을 때 되돌릴 수 있도록.

## 3. 후보 풀 수집

> **인기 top 100만 쓰면 다 아는 노래뿐이라 추천의 의미가 약하다.**
> 핵심 아이디어: **아티스트를 모은 뒤 그 카탈로그를 펼친다.** 아티스트를 어디서 얻든
> 이후 파이프라인(§3.2~3.3)은 동일하다.

### 3.0 아티스트 소스 3가지

| 소스 | 성격 | 갱신 | `origin` |
|---|---|---|---|
| **Apple 차트** (§3.1) | 지금 유행하는 곡 | 자동(주간) | `chart` |
| **설문** (§3.6) | 사람들이 실제 아끼는 가수 — 옛날 곡·인디·발라드 포함 | 수동(가끔) | `survey` |
| **사용자가 붙인 곡** | 실사용 취향, 진짜 롱테일 | 자동(누적) | `user` |

- 차트는 **최신**을, 설문은 **시대·장르 폭**을, 사용자 곡은 **개별 취향**을 담당한다. 셋은 대체가 아니라 보완.
- 서비스 초기엔 사용자 곡이 없으므로 **설문이 그 빈자리를 메운다**(콜드 스타트 대응).

### 3.1 Apple RSS 차트 (실측 확인)
```
GET https://rss.marketingtools.apple.com/api/v2/{kr|us}/music/most-played/100/songs.json
```
- **최대 100곡**(200은 빈 응답). 무인증·무료.
- 주는 것: `id`(트랙ID), `artistId`, `name`, `artistName`, `genres[]`, `artworkUrl100`
- previewUrl 없음 → §3.3에서 확보
- ⚠ **장르별 차트는 폐기됨** — 구 `itunes.apple.com/{kr}/rss/topsongs/genre=51` 은 빈 응답.
  장르 다양성은 차트의 `genres[]`와 카탈로그 확장으로 대체.

### 3.2 아티스트 카탈로그 확장 (핵심, 실측 확인)
```
GET https://itunes.apple.com/lookup?id={artistId}&entity=song&limit=50&country=kr
```
- 그 아티스트의 곡을 한 번에 반환. **previewUrl 포함**.
- 실측: 코르티스 조회 시 히트곡(REDRED) 외 수록곡(FaSHioN·Blue Lips·Wassup)이 함께 나옴.
- 첫 결과는 `wrapperType="artist"`(아티스트 정보) → **건너뛰고 `wrapperType="track"`만** 취한다.

### 3.3 수집 흐름
```
RSS 차트(kr, us) → 아티스트 ID 추출(중복 제거)
                 → 아티스트별 카탈로그 lookup (50곡)
                 → tracks upsert (origin='chart', genre, previewUrl 저장)
```
- 차트 곡 자체도 `lookup?id={트랙ID들}`(콤마 묶음)로 previewUrl 받아 함께 적재.

### 3.4 규모 & 비용
| | 값 |
|---|---|
| 차트 | 100곡 × 2개 스토어프론트 |
| 고유 아티스트 | 약 80명 × 2 |
| 아티스트당 곡 | **50곡**(설정값) |
| **최종 풀** | **약 4,000~6,000곡** (대부분 수록곡 = 덜 알려진 곡) |
| 최초 감정값 채우기 | 약 5,000 요청 = bulk 100회 (§1 비용 참고) |
| 이후 주간 | 신규 아티스트만 → 수분 |

- 부담되면 `아티스트당 곡 수`를 30으로 낮추면 시간도 비례해 감소.
- **풀은 누적** — 차트에서 빠져도 `tracks`에 남는다.

### 3.5 제외 규칙
- `previewUrl` 없는 곡 (분석·재생 불가)
- 앨범명에 `DJ Mix` 포함 (실측 시 믹스 트랙이 섞여 나옴)
- 필요 시 `trackName`에 `(Live)`·`(Inst.)`·`(Remix)` 포함 곡

### 3.6 설문으로 아티스트 모으기

차트에 안 잡히는 가수(옛날 곡·인디·밴드·발라드)를 확보하는 수동 경로.
가수 이름만 있으면 **§3.2와 같은 카탈로그 확장**을 태우면 되므로 추가 구현이 거의 없다.

```
설문 응답(가수 이름) → iTunes 검색으로 artistId 확보 → 카탈로그 lookup(§3.2) → tracks(origin='survey')
```

**이름 → artistId 얻는 법 (둘 중 하나)**
- `search?term={가수명}&entity=musicArtist&country=kr` → `artistId`
- 또는 기존 곡 검색(`entity=song`) 결과의 `artistId` 필드를 그대로 사용
  (앱이 이미 쓰는 엔드포인트라 클라이언트 재사용 가능)

> ⚠ 위 두 방식은 문서 작성 시점에 외부에서 응답 확인을 못 했다(도구 제약).
> 구현 시 실호출 1회로 `artistId` 필드를 확인할 것. `lookup?id={artistId}&entity=song`은 확인 완료.

**설문 설계 — 기분별로 물으면 일석이조**

단순히 "좋아하는 가수"보다 **기분별로** 묻는 편이 좋다.

```
· 슬플 때 듣는 가수/곡은?
· 신날 때 듣는 가수/곡은?
· 평온할 때 듣는 가수/곡은?
· 화날 때 듣는 가수/곡은?   (1인당 3~5개, 30~50명)
```

이유 두 가지:
1. **감정 커버리지 확보** — 그냥 물으면 응답이 한쪽(예: K-Pop)에 쏠려 `슬픔`·`화남` 좌표 근처가 빈다.
2. **튜닝 데이터가 공짜로 생긴다** — "슬플 때 듣는 곡"들의 valence 평균이
   §5.1의 `슬픔` 목표 좌표(0.15, 0.25)와 맞는지 대조할 수 있다. §8-5의 "실제 청취 튜닝"을
   **감으로 하지 않고 데이터로** 할 수 있게 된다.

**한계**
- 표본 편향(주변 지인 위주) — MVP에선 오히려 타깃 사용자와 가까워 유리하나, 확장 시 재수집 필요.
- 자동 갱신이 안 됨 → 차트(자동)와 반드시 병행.

## 4. 감정값 채우는 배치

### 규칙 하나로 끝
```sql
SELECT * FROM tracks
WHERE valence IS NULL AND preview_url IS NOT NULL
```
- 차트·설문·사용자 곡을 **구분하지 않는다.** "감정값 없고 미리듣기 있으면 채운다"가 전부.
- `preview_url` 없는 곡은 자동 제외 — 앱에서 재생도 안 되므로 후보에서 빠지는 게 맞다.

### 조회
```
POST /bulk        (최대 50곡/요청, 이름+아티스트로 조회)
```
- 카탈로그에 없으면 **백필**로 자동 분석·등재(약 15초). 결과는 재조회로 수령.
- 받은 값 저장: `valence`, `energy`(→arousal), `acousticness`, `tempo`,
  `features_source='freqblog'`, `features_fetched_at=now`.
- `429`(쿼터·동시성)는 `Retry-After` 존중하고 다음 배치로 미룬다.

### 주기
- 감정값은 변하지 않으므로 **곡당 한 번만** 조회 → 이후 영구 캐시.
- 주 1회. 사용자가 오늘 붙인 곡은 다음 배치 후 후보가 된다(지연 무관).

## 5. 추천 흐름 & 곡 선택 규칙

```
1. 목표 좌표 계산              (기존 MoodWeatherSeasonMapper 그대로)
2. tracks에서 후보 조회         valence·energy 채워진 곡 전체
3. 최근 추천 곡 제외            해당 유저에게 최근 14일 내 추천된 곡 제외
4. 점수 계산 후 정렬            §5.1
5. 상위 30곡 중 **고정 시드로** 1곡 (§5.4)
6. 감정값 있는 곡이 없으면 → 기존 랜덤 폴백 (앱은 항상 곡을 반환)
```

### 5.1 점수 = 목표 좌표와의 거리 − 취향 가산점
```
score = 1.0 × (곡.valence − 목표.valence)²
      + 1.0 × (곡.arousal − 목표.arousal)²
      + (날씨가 '비'이면 0.5 × (1 − 곡.acousticness)² )
      − 취향 가산점
```
| 항목 | 값 | 의미 |
|---|---|---|
| wV / wA | 1.0 / 1.0 | valence·arousal 동등 |
| wAc (비) | 0.5 | 비 오는 날 어쿠스틱 가중 |
| seed 아티스트 일치 | −0.15 | **조금만 반영** — 같은 가수면 유리하되 독점 안 함 |
| seed 장르 일치 | −0.05 | 비슷한 분위기 소폭 우대 |
| **한국 곡** | **−0.03** | 한국어 곡 우선(§5.3). 동점 처리용 — 값을 키우면 감정 매칭을 압도하므로 주의 |
| 상위 K | **30** | 최적 1곡이 아니라 상위 30곡 중 선택. 같은 조건이 반복돼도 곡이 안 겹치도록 넓게 잡는다(풀이 수천 곡이라 30등도 충분히 가깝다) |

> seed는 **후보를 좁히지 않는다.** 1단계처럼 "seed 아티스트만 검색"하면 같은 가수만
> 반복되므로(취향 감옥), 후보는 전체로 두고 점수만 조금 깎아준다.

### 5.2 최근 추천 곡 제외
- 윈도우 **14일**. 같은 유저에게 2주 안에 추천된 곡은 후보에서 뺀다.
- 판정은 기존 `diary_tracks`(role=RECOMMENDED) + 일기 날짜로 조회.

### 5.3 한국 곡 우선

후보 풀에 국내·해외 곡이 섞여 있으므로, 감정 거리만 보면 영어 곡이 자주 뽑힌다.
**한국 곡에 가산점(−0.03)**을 줘서 우선하되 해외 곡도 배제하지 않는다.

**판별 방법** — 수집 시점에 `artistName`에 한글(가~힣)이 있으면 `is_korean=true`로 저장.
- 실측 근거: Apple `kr` 스토어프론트는 국내 아티스트를 **한글 표기로** 준다
  (코르티스·제니·레드벨벳·아일릿 → 한글 / Post Malone·Ariana Grande → 영문).
- 기존 `MoodWeatherSeasonMapper.storefront()`의 한글 판별 로직을 재사용한다.
- 저장 시 1회 계산해 컬럼에 넣으므로 조회 때 비용이 없다.

> **가산점 크기 주의** — 검증 계산 결과 0.12는 과했다. 가산점 b는 "한 축에서 √b 만큼 벗어나도
> 이긴다"는 뜻이라, 0.12면 약 0.35(35%) 벗어난 한국 곡이 좌표가 정확한 해외 곡을 이긴다.
> 상위권 후보들의 점수 차가 보통 0.01~0.05인 점을 고려해 **0.03**으로 낮췄다.
> 더 키우려면 가산점보다 `is_korean` 필터가 결과를 예측하기 쉽다.

### 5.4 같은 조건이면 같은 곡 (결정성)

**문제**: 요청마다 랜덤을 굴리면 새로고침할 때마다 곡이 바뀌어 "오늘의 곡" 느낌이 사라진다.

**해결**: 상위 5곡 중 고를 때 난수 대신 **고정 시드**를 쓴다.
```
seed  = hash(userId, date, mood, weather)
index = seed % min(30, 후보수)
```
- 같은 사람이 같은 날 **같은 조건**으로 요청하면 → 항상 **같은 곡**
- 기분이나 날씨를 **바꾸면** → 다른 곡 (조건이 바뀌었으므로 자연스러움)
- **DB 저장이 필요 없다.** 추천 API는 그대로 무상태로 둔다.

> 후보 풀이 바뀌면(주 1회 배치) 결과도 바뀔 수 있으나, 하루 안에서는 안정적이다.

**K를 30으로 잡은 이유** — 같은 계절에 같은 기분·날씨가 반복되면 목표 좌표가 거의 같아
상위 목록도 같아진다. K가 작으면(예: 5) 그 5곡만 돌려막게 되므로, 넓게 잡아 한 달 이상
반복돼도 곡이 겹치지 않게 한다. 14일 제외(§5.2)와 함께 작동한다.

## 6. 스키마 변경

| 컬럼 | 타입 | 용도 |
|---|---|---|
| `tracks.origin` | VARCHAR(10) | `user`(일기 유입) / `chart`(차트 배치) / `survey`(설문 수집). 지금은 모두 후보로 쓰지만 나중에 좁힐 수 있게 구분만 해둔다 |
| `tracks.genre` | VARCHAR(50) | seed 장르 가산점(§5.1)용. iTunes `primaryGenreName` 저장 |
| `tracks.is_korean` | BOOLEAN | 한국 곡 가산점(§5.3)용. 수집 시 아티스트명 한글 여부로 판정 |

- `valence`·`energy`·`acousticness`·`tempo`·`features_source`·`features_fetched_at`는 **이미 있음**.

## 7. 설정값 정리

```yaml
recommendation:
  chart:
    storefronts: [kr, us]   # kr만으로 줄이려면 여기서 제거
    limit: 100              # RSS 상한
    songs-per-artist: 50    # 아티스트당 카탈로그 곡 수 (풀 크기·배치 시간 조절)
    cron: 주 1회
  scoring:
    weight-valence: 1.0
    weight-arousal: 1.0
    weight-acoustic-rain: 0.5
    bonus-same-artist: 0.15
    bonus-same-genre: 0.05
    bonus-korean: 0.03      # 동점 처리용. 키우면 감정 매칭을 압도함(0.12는 과함)
    top-k: 30
  exclude-recent-days: 14
  deterministic: true       # 같은 조건이면 같은 곡 (§5.4)
```

## 8. 남은 작업

### 구현 순서
1. **차트 수집 배치** (§3.1~3.3) — RSS + 카탈로그 확장 → `tracks` 채우기
   1-b. **설문 수집** (§3.6) — 설문 진행 후 가수 목록을 같은 파이프라인에 투입
2. **감정값 배치** (§4) — FreqBlog 키 발급 → bulk 조회 → `tracks` 채우기
3. **추천 로직 교체** (§5) — DB 조회 + 점수 + 고정 시드
4. **스키마 마이그레이션** (§6) — `origin`·`genre`·`is_korean` 추가

### 구현 착수 전 확인할 것 (외부 실호출 필요)
| 항목 | 확인 방법 |
|---|---|
| FreqBlog `/bulk` 요청·응답 형태, 백필 재조회 방식 | 무료 키 발급 후 1회 호출 |
| FreqBlog 한국 곡 적중률 | 국내 곡 10개 정도로 테스트 |
| iTunes 이름 → `artistId` 필드명 (설문 경로) | `search?entity=musicArtist` 1회 호출 |

### 운영 결정 (확정)

**배치 실행 위치** — **앱 안 `@Scheduled` + 수동 트리거 엔드포인트**
- API 서버는 어차피 상시 가동이므로 별도 프로세스를 둘 이유가 없다. 엔티티·리포지토리도 그대로 재사용.
- `POST /admin/batch/chart`, `POST /admin/batch/features` — 관리자 인증 필수.
- 자동: 주 1회 스케줄. 수동: 개발 중 즉시 실행 + **배포 직후 운영 DB 초기 적재**에 사용.
- ⚠ 서버를 여러 인스턴스로 늘리면 중복 실행 방지(락)가 필요 — 현재 단일 인스턴스 전제.

**콜드 스타트** — **출시 전 수동 배치 1회**
- 로컬에서 먼저 돌려 동작 확인 → 배포 후 운영 서버의 수동 트리거를 호출해 운영 DB 적재.
- ⚠ **로컬 배치는 로컬 DB만 채운다.** 운영 DB는 별도로 한 번 돌려야 한다.
- 적재 전에는 `track: null`이 나가므로, 출시 전 반드시 수행.

**튜닝 시점** — **구현 완료 후**
- 값(기분 좌표·Δ·가중치·가산점·K·윈도우)은 모두 시작값이며 검증되지 않았다.
- 순서: ① 직접 여러 조건으로 뽑아 들어보고 큰 오류 교정 → ② 설문 데이터로 valence 검증(§3.6)
  → ③ 출시 후 저장률 등 실사용 신호로 장기 조정.

### 정리 대상
