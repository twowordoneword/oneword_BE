# 설문 초안 — 기분별 애청곡 수집

> 이번 설문의 목적은 **두 가지**다.
>
> 1. **후보 풀 씨앗** — 차트에 안 잡히는 가수(옛날 곡·인디·발라드)를 확보한다. 응답에서 **가수**를 뽑아 카탈로그를 펼친다.
> 2. **제품 검증** — 이 앱을 실제로 쓸 사람이 있는지, 어떤 문제를 풀어야 하는지 확인한다.
>
> 📌 **기분별 곡 수집(튜닝 데이터)은 이번에 하지 않는다.** 지금은 파이프라인과 서비스가
> 돌아가는지 확인하는 단계라 곡 하나면 충분하다. 기분 좌표 검증은 §11에 별도 과제로 남긴다.

## 1. 설문 설계 원칙 (읽고 시작할 것)

### 1.1 서비스 설명은 맨 마지막에

**서비스를 소개하는 순간부터 뒤의 모든 답이 오염된다.** "음악 일기 앱을 만드는데요..." 를 먼저 말하면
응답자는 그때부터 *만든 사람을 도와주려고* 답한다. 없던 니즈도 생겼다고 말한다.

```
[나쁨] 서비스 소개 → "쓰실 건가요?"           → 대부분 "네" (사회적 압력)
[좋음] 평소 행동 질문 → ... → 마지막에 소개   → 앞의 답이 진짜 데이터로 남는다
```

### 1.2 미래가 아니라 과거를 묻는다

사람은 자기 미래 행동을 예측하지 못한다. 대신 **이미 한 일**은 사실이다.

| 나쁜 질문 | 좋은 질문 | 이유 |
|---|---|---|
| "이런 앱 쓰실 건가요?" | "일기 앱을 써본 적 있나요? 마지막으로 쓴 게 언제예요?" | 의향은 부풀려지고 기록은 정확하다 |
| "매일 기록할 의향이 있나요?" | "최근 한 달에 몇 번 기록했나요?" | 실제 빈도가 드러난다 |
| "어떤 기능을 원하세요?" | "그만두게 된 이유가 뭐였어요?" | 원하는 기능보다 **막힌 지점**이 값지다 |

### 1.3 기능 목록을 그냥 나열하지 않는다

"원하는 기능을 모두 고르세요"는 **전부 선택되어 아무 정보가 없다.** 공짜니까 다 고른다.
정보를 얻으려면 **하나만 고르게** 하거나 **버리게** 해야 한다.

```
[나쁨] 원하는 기능을 모두 고르세요 → 8개 중 7개 선택됨 → 우선순위 없음
[좋음] 이 중 하나만 남긴다면?      → 강제 선택 → 진짜 우선순위가 나옴
```

### 1.4 만든 사람이 묻는다는 사실은 못 숨긴다

Part D에서 앱을 소개하는 순간, 응답자는 **이게 당신 작품이라는 걸 안다.** 그때부터
"별로다"라고 쓰기 어려워진다. 순서를 뒤로 미뤄도 이 편향은 남는다.

**그래서 Part D의 긍정 응답은 신뢰하지 않는다.** "써볼 것 같다"는 실제 사용률을 크게 부풀린다.
대신 다음 네 가지로 신호를 건진다.

| 기법 | 문항 | 왜 통하나 |
|---|---|---|
| **사전 부검(premortem)** | "이 앱이 6개월 뒤 사라진다면 이유가 뭘까요?" | 부정이 **기본값**이라 비판이 예의에 어긋나지 않는다 |
| **비교 강제 선택** | "지금 쓰는 방법 vs 이 앱, 어느 쪽?" | 예의상 둘 다 좋다고 할 수 없다 |
| **행동 요구** | "출시되면 알림 받으실래요? 이메일" | **말이 아니라 행동**이라 부풀려지지 않는다 |
| **제3자 화법** | "친구가 이걸 쓴다면 뭐라고 하시겠어요?" | 심리적 거리가 생겨 솔직해진다 |

> 📌 **진짜 데이터는 Part B·C에 있다.** 앱을 모르는 상태에서 답한 "일기를 왜 그만뒀는지",
> "노래를 어떻게 고르는지"가 Part D의 어떤 응답보다 값지다. Part D는 참고용으로만 본다.

### 1.5 그 외

- **한 문장에 두 가지를 묻지 않는다** — "앱이 예쁘고 쓰기 편한가요?"는 어느 쪽 답인지 모른다.
- **형용사로 유도하지 않는다** — "이 *편리한* 기능을..." 은 답을 정해둔 질문이다.
- **개방형을 먼저, 선택형을 나중에** — 선택지를 먼저 보여주면 그 안에서만 생각한다.
- **"모름/없음" 선택지를 반드시 넣는다** — 없으면 억지로 아무거나 고른다.

## 2. 음악 문항 설계 (Part A 근거)

이번엔 **곡 하나만** 받는다. 이유:

- 지금 필요한 건 **가수 목록**이다. 그걸로 카탈로그를 펼치면 한 명당 곡 10개가 나오므로,
  응답자에게 여러 곡을 받을 이유가 없다.
- 목적이 **DB·파이프라인·서비스가 실제로 돌아가는지 확인**하는 것이라 데이터 정밀도보다
  응답 수가 중요하다. 문항이 짧을수록 응답률이 오른다.
- 기분별로 나눠 받는 건 **좌표 튜닝**을 위한 것인데, 그건 서비스가 돌아가는 걸 확인한 뒤의 일이다(§11).

**4. 일기나 감정 기록을 해본 적이 있나요?**

## 7. 분량 주의 — 길면 아무도 안 끝낸다

전체 15문항은 **6~7분**짜리다. 응답률이 눈에 띄게 떨어지는 길이다. 선택지:

| 방식 | 장점 | 단점 |
|---|---|---|
| **전부 한 번에** | 같은 사람의 취향과 의견을 연결해 볼 수 있다 | 이탈률↑, 뒤 문항 성의 없어짐 |
| **둘로 쪼개기** | Part A만 먼저 → 응답 많이 확보 / Part B~D는 소수에게 깊게 | 두 번 부탁해야 함 |
| **줄이기** | Part A(1문항) + 5·8·13·15번만 → 2~3분 | 정보량 감소 |

> **줄인다면 이 4개는 남길 것**: 5번(그만둔 이유), 8번(노래 고르는 방식),
> 13번(실패 이유), 15번(알림 이메일). 앞의 둘은 오염 없는 데이터, 뒤의 둘은 편향에 강한 신호다.

> 필수 응답으로 걸지 말 것. 개방형을 필수로 만들면 아무 글자나 적고 넘어간다.

## 8. 목표 인원과 예상 결과

| 항목 | 예상 |
|---|---|
| 응답자 | **30~50명** |
| 1인당 응답 곡 | 1곡 (+ 선택 문항의 가수 몇 명) |
| 중복 제거 후 가수 | **약 30~50명** |

> ⚠️ **가수 30~50명은 후보 풀로는 얇다.** 곡 10개씩이면 300~500곡이다.
> 하루 한 곡 추천에는 돌아가지만 감정 다양성이 부족할 수 있으므로,
> **차트 수집(수동 트리거)을 함께 돌려 합치는 것을 전제로 한다.**

### 후보 풀 크기 계산

```
(설문 가수 + 차트 가수) × 아티스트당 N곡 = 최종 풀
```

| 구성 | 가수 | 아티스트당 곡 | 후보 풀 | FreqBlog 무료(월 1,000건) |
|---|---|---|---|---|
| 설문만 | 40명 | 10곡 | 약 400곡 | 첫 달 완료 (여유) |
| **설문 + 차트** | **약 190명** | **10곡** | **약 1,900곡** | 2개월 |
| 설문 + 차트 | 약 190명 | 5곡 | 약 950곡 | **첫 달 완료** ✅ |

> **설문 수집은 `songsPerArtist: 10`, 차트 수집은 5로 시작하는 것을 권한다.**
> 약 1,000곡이면 첫 달에 감정값까지 다 채워지고, 품질을 확인한 뒤 늘리면 된다.

## 9. 응답 → 시스템 반영

### 9.1 가수 → 후보 풀

```
엑셀 응답 → 가수 이름만 추출·중복 제거 → POST /api/v1/admin/batch/survey
          → iTunes에서 artistId 조회 → 카탈로그 확장 → tracks(origin='SURVEY')
```

가수 이름만 있으면 되므로 **곡명은 이 경로에 필요 없다.**

### 9.2 곡 → 후보 풀 보강

1번 응답의 곡 자체도 `tracks`에 넣을 수 있으나, 어차피 그 가수의 카탈로그에 대부분 포함되므로
**따로 처리하지 않는다.** 곡명은 "이 가수가 맞나" 확인용으로만 본다.

## 10. 한계 (기록해 둘 것)

- **표본 편향** — 주변 지인 위주라 특정 연령·취향에 쏠린다. MVP 타깃과 가까우면 오히려 유리하지만, 사용자층이 넓어지면 재수집이 필요하다.
- **자동 갱신이 안 된다** — 설문은 한 시점의 스냅샷이다. 신곡은 차트 수집(3.1)이 담당하므로 **둘을 병행**해야 한다.
- **응답 표기 흔들림** — "아이유"/"IU", "BTS"/"방탄소년단"처럼 같은 가수를 다르게 적는다. 수집 시 중복이 생기지만, `tracks`의 `(name, artist)` 유니크 제약이 곡 단위 중복은 막아준다.

## 11. 다음 설문에서 할 것 — 기분 좌표 튜닝

이번 설문은 곡 하나만 받으므로 **기분 좌표는 여전히 추측값**으로 남는다.
서비스가 돌아가는 걸 확인한 뒤, 튜닝을 위해 짧은 2차 설문을 돌린다.

**문항 (한 칸, 장문형)**
```
신날 때 :
편안할 때 :
울적할 때 :
화날 때 :
```

**활용**
```
"울적할 때" 응답 50곡 → 감정값 배치로 valence 채움 → 평균 계산
                                                   ↓
                             추측값 0.15 vs 실측 평균 0.22 → 좌표를 0.22로 교체
```

**함께 확인할 것**
- 문항별 valence 평균이 **실제로 갈리는가?** (신남 > 편안 > 울적)
  안 갈리면 valence 가중치를 낮추고 장르를 보조 신호로 써야 한다.
- 슬픔과 우울이 구분되는가? (현재 좌표가 0.07밖에 안 떨어져 사실상 같은 결과가 나온다)

> valence는 모델 정확도가 낮은 축(R² 0.3~0.5)이라 이 검증의 값이 크다. 미루되 잊지 말 것.
